## Problem Statement

团队里的业务人员（运营、产品、销售、创业团队成员）手上常有 CSV/Excel 表格，想快速回答"上个月哪个省份的 GMV 涨得最快""哪个套餐的流失最高"这类问题，并把结论做成图表给同事和客户看。现有的做法都不好用：

- Excel 透视表和手工画图，每换一个问题就要重做一遍，也没法和同事共享分析过程；
- 找数据分析师写 SQL，要排队，沟通成本高；
- 传统 BI 工具需要先建模、配置数据源、学拖拽界面，门槛太高，对"一份表格、几个问题"的场景来说太重；
- 把表格直接丢给通用聊天机器人，图表不可控、不可复用，也没法团队协作和安全地对外分享，而且整份数据都要交给第三方。

## Solution

问数（WenShu）是一个面向团队的对话式数据分析 SaaS。用户在 **Workspace** 中上传表格得到 **Dataset**，系统自动生成 **Profile**；用户可以补充 **Column Description**。成员针对某个 Dataset 发起 **Conversation**，用中文提 **Question**；AI 生成查询，在用户自己的浏览器里执行（原始数据不离开浏览器，发给 AI 的只有列结构和少量样本行），并给出包含结论文字和最多一个 **Chart** 的 **Answer**。用户可以不经过 AI 手动调整图表，也可以把满意的图表 **Pin** 到 **Board** 上排版，再通过可撤销、可设过期时间的 **Share Link** 发给外部的人：对方只看到图表，看不到原始数据和对话。

团队通过 Invite Link 邀请成员，按 Owner、Editor、Viewer 三种 Role 协作。面试官和访客可以点"一键体验"，以 **Guest** 身份进入一份预置好的演示工作区，无需注册。

## User Stories

### 访问与身份

1. 作为第一次访问的人，我想在首页看到产品介绍和"一键体验"按钮，以便不注册也能马上试用。
2. 作为访客，我想点"一键体验"后直接进入一份预置好的演示工作区（包含数据集、会话和看板），以便几秒内看到产品的完整能力。
3. 作为 Guest，我想拥有一份独立的演示工作区副本，以便我的操作不会影响其他访客，也不会看到其他访客的数据。
4. 作为 Guest，我想知道自己的演示数据会在 24 小时后被清理，以便对数据的去留有预期。
5. 作为访客，我想用邮箱和密码注册账号，以便长期使用产品。
6. 作为访客，我想用 GitHub 账号登录，以便不用再记一个密码。
7. 作为用户，我想登录后自动回到上次访问的工作区，以便继续工作。
8. 作为未登录的人，我想在访问工作区页面时被引导到登录页，并在登录后回到原来的页面，以便不丢失上下文。
9. 作为用户，我想退出登录，以便在公共电脑上保护账号安全。
10. 作为新注册的用户，我想系统自动为我创建一个工作区，以便注册后马上就能上传数据。

### 工作区与成员

11. 作为用户，我想新建更多的工作区，以便把不同团队或项目的数据分开。
12. 作为用户，我想在我加入的多个工作区之间切换，以便在不同团队间工作。
13. 作为 Owner，我想生成指定 Role 的 Invite Link，以便邀请同事以合适的权限加入。
14. 作为收到 Invite Link 的人，我想登录或注册后通过链接加入工作区，以便开始协作。
15. 作为 Owner，我想修改成员的 Role，以便随着职责变化调整权限。
16. 作为 Owner，我想移除成员，以便离职或项目结束的人不能再访问数据。
17. 作为成员，我想主动退出一个工作区，以便清理我不再需要的工作区。
18. 作为最后一个 Owner，我想在退出之前被要求先把 Owner 转交给别人，以便工作区不会变成没人管理的状态。
19. 作为 Owner，我想删除整个工作区，以便彻底清除其中的全部数据。
20. 作为成员，我想看到被移除的人创建的会话和看板仍然保留，创建者显示为"前成员"，以便团队的分析成果不会因为人员变动而丢失。
21. 作为 Viewer，我想看到所有数据集、会话和看板，但看不到修改类的按钮，以便界面上不出现我无权执行的操作。
22. 作为任何成员，我想在试图访问其他工作区的资源时被拒绝，以便团队之间的数据完全隔离。
23. 作为 Guest，我不能创建 Invite Link，也不能新建工作区，以便演示环境不被滥用。

### 数据集

24. 作为 Editor，我想上传 CSV 文件得到一个 Dataset，以便对它提问。
25. 作为 Editor，我想上传 XLSX 文件，以便不用先在 Excel 里另存为 CSV。
26. 作为 Editor，我想在上传过程中看到分阶段的进度（解析、生成概览、转换格式、上传、确认），以便知道还要等多久。
27. 作为 Editor，我想取消一个正在进行的上传，以便传错文件时及时止损。
28. 作为 Editor，我想在文件超过大小上限（普通用户 50MB，Guest 10MB）时立刻得到明确提示，而不是传到一半才失败。
29. 作为 Editor，我想让系统自动识别每一列的类型（日期、数值、类别、文本），以便 AI 能正确理解数据。
30. 作为成员，我想查看数据集的 Profile：每列的空值率、去重数、最小值和最大值、迷你分布图，以便在提问之前先了解数据的全貌。
31. 作为 Editor，我想给列补充 Column Description（比如"gmv：成交总额，单位元"），以便 AI 更准确地理解业务含义。
32. 作为 Editor，我想在数据更新后重新上传得到一个新的 Dataset，而已有的看板不受影响，以便历史结论保持可复现。
33. 作为上传者本人或 Owner，我想删除一个 Dataset，以便清理过时或上传错误的数据。
34. 作为删除 Dataset 的人，我想事先被告知它的会话会一起被删除，而看板上 Pin 过的图表会保留下来，以便我了解删除的影响。
35. 作为看板的读者，我想在来源 Dataset 被删除后仍然看到图表，并看到"数据集已删除"的标记，以便已经分享出去的看板不会突然缺图。
36. 作为 Guest，我想看到预置的"电商订单"和"SaaS 订阅收入"两份演示数据集，以便马上有能用来提问的数据。

### 分析会话

37. 作为 Editor，我想针对一个 Dataset 新建 Conversation，以便开始用自然语言分析数据。
38. 作为 Editor，我想在新会话的空状态里看到 3 个根据列结构生成的 Suggested Question，以便不知道问什么时有个起点。
39. 作为会话创建者，我想用中文提问，并看到 AI 逐字流式输出回答，以便不用干等。
40. 作为会话创建者，我想看到 Answer 里有一段结论文字和最多一个图表，以便一眼看到结论和对应的证据。
41. 作为会话创建者，我想展开查看生成图表所用的查询，以便核对 AI 的计算口径。
42. 作为会话创建者，我想在 AI 生成的查询出错时，让 AI 自动根据报错修正（最多 3 轮），以便不用自己去理解 SQL 报错。
43. 作为会话创建者，我想在问题超出数据范围（比如数据里没有成本字段却问利润率）时，得到一段说明和 2 到 3 个可以问的推荐问题，而不是一张胡乱拼凑的图。
44. 作为会话创建者，我想在生成过程中点击停止，以便及时打断方向不对的回答。
45. 作为会话创建者，我想对"已中断"或"失败"的 Answer 点击重新生成，以便不用重新输入问题。
46. 作为会话创建者，我想在系统或模型出错导致 Answer 失败时退还这次的额度，以便不为系统的问题买单。
47. 作为会话创建者，我想基于上下文继续追问（比如"按省份拆开看"），以便层层深入分析。
48. 作为工作区成员，我想查看同事的会话（只读），以便了解他们的分析过程。
49. 作为 Editor，我想把同事的会话 Fork 成我自己的会话再继续追问，以便在他们的基础上继续分析，又不打乱原来的会话。
50. 作为会话创建者或 Owner，我想删除会话，以便清理无用的分析。
51. 作为用户，我想随时看到今天还剩多少 AI Quota，以及额度何时重置（北京时间 0 点），以便合理安排提问。
52. 作为额度已经用完的用户，我想看到输入框被禁用并提示重置时间，而不是提问后才报错。
53. 作为会话的读者，我想打开一个很长的会话时页面依然流畅，并且直接定位到最新一条，以便快速看到最新结论。
54. 作为正在看 AI 输出的人，我想在 AI 输出时视图自动跟随到底部；我向上翻阅历史时不被拉回去；想回到最新内容时能点"回到底部"按钮，按钮在有新内容时带提示点。
55. 作为正在阅读历史回答的人，我想在上方的图表加载完成时，我正在看的内容不会跳动。
56. 作为系统设置了"减少动画"的人，我想页面不播放平滑滚动动画。
57. 作为 Viewer 或手机用户，我想打开会话就能直接看到所有图表，不需要等待查询引擎和原始数据下载。

### 图表

58. 作为会话创建者，我想不经过 AI、直接在面板里切换图表类型、更换 x/y 字段、修改排序，以便快速微调 AI 给出的图。
59. 作为调整图表的人，我想在只切换图表类型时立即看到结果，只有改了字段或聚合方式时才重新查询。
60. 作为用户，我想看到柱状图（含堆叠）、折线图和面积图、饼图和环形图、散点图、表格、热力图、中国省份地图、KPI 数字卡这几类图表，以便用合适的形式表达不同的结论。
61. 作为用户，我想在暗色模式下看到配色协调的图表，以便长时间使用不刺眼。
62. 作为用户，我想把鼠标悬停在图表上看到具体数值（tooltip），以便读出精确的数字。
63. 作为用户，我想在数据点很多的折线图和散点图上依然有流畅的交互，以便处理数据量较大的情况。

### 看板

64. 作为 Editor，我想新建一个 Board，以便整理一组相关的结论。
65. 作为 Editor，我想把会话里的图表 Pin 到某个看板，以便把分析成果沉淀下来。
66. 作为 Editor，我想在 Pin 之后继续在会话里修改原图，而看板上的那张图保持不变，以便看板内容稳定。

75. 作为 Guest，我想看到一个预置的"经营周报"看板和 2 到 3 个示例会话，以便立刻看到最终效果。

## Implementation Decisions

### 总体架构

- **Next.js App Router 全栈单体**（ADR-0008）。后端分三层：路由层只做请求适配；业务用例层承载全部业务规则和授权，不依赖任何 Next.js API；数据访问层基于 Drizzle + Postgres，每个读写函数都强制要求传入 workspaceId，写不出不带工作区过滤的查询。
- **写操作**全部用 Server Action，经过统一的包装函数：Zod 校验入参 → 读取会话 → 校验工作区成员身份和角色 → 执行业务用例 → 返回 `{ ok: true, data } | { ok: false, error: { code, message } }`。业务上可预期的错误（权限不足、额度用完、资源不存在）返回错误码，不抛异常。
- **读操作**由 RSC 直接调用业务用例层。
- **Route Handler** 只用于四类场景：AI 流式输出、签发上传用的预签名 URL、拉取快照、定时任务入口。不用 tRPC，不对外提供 REST API。
- **middleware（proxy）** 只做"没有登录 cookie 就重定向到登录页"，不承担授权。
- **基础设施**只有 Postgres、S3 兼容的对象存储和应用本身，不用 Redis、不用消息队列（ADR-0010）。本地开发用 Docker Compose 运行 Postgres 和 RustFS（兼容 S3；MinIO 已停止发布社区版 Docker 镜像）。

### 身份认证与授权

- **Better Auth** 负责身份认证：邮箱密码、GitHub OAuth、会话管理（ADR-0001）。不使用它的 organization 插件，Workspace、Member、Role 自己建模。
- **不做**邮箱验证和找回密码。
- **Guest**：点"一键体验"时创建一个带过期时间的 User，并把演示工作区（数据集、会话、看板、快照）复制一份给他，他在副本里是 Owner。
- **权限矩阵**（在业务用例层执行，是集成测试的直接依据）：

| 操作 | Owner | Editor | Viewer |
|---|---|---|---|
| 查看数据集、会话、看板 | ✅ | ✅ | ✅ |
| 上传数据集、编辑列说明 | ✅ | ✅ | ❌ |
| 删除数据集（连同它的会话） | ✅ | 仅上传者本人 | ❌ |
| 新建会话、Fork 会话 | ✅ | ✅ | ❌ |
| 在会话里继续追问 | 仅创建者 | 仅创建者 | ❌ |
| 删除会话 | ✅ | 仅创建者 | ❌ |
| 新建看板、Pin、编辑看板 | ✅ | ✅ | ❌ |
| 删除看板 | ✅ | 仅创建者 | ❌ |
| 创建、撤销分享链接 | ✅ | ✅ | ❌ |
| 管理成员、邀请、修改角色、删除工作区、转交 Owner | ✅ | ❌ | ❌ |

  Guest 另外不能创建 Invite Link，也不能新建工作区。每个工作区至少要有一个 Owner。
- 客户端的 `useCan` 只用于隐藏或禁用按钮，真正的校验永远在服务端。

### 数据模型（实体与关键规则）

- **User**：包含是否为 Guest 以及 Guest 的过期时间。
- **Workspace**：包含可读、可修改的 slug（用于 URL）。
- **Member**：(User, Workspace, Role) 三元组；成员离开后删除这一行，但他创建的内容保留创建者引用，界面上显示为"前成员"。
- **Invite Link**：包含工作区、Role、一次性令牌、使用状态。
- **Dataset**：包含状态（等待上传确认 / 就绪）、列结构、Profile、少量样本行、Column Description、对象存储中的位置、文件大小、上传者。上传后除 Column Description 外不可修改。
- **Conversation**：关联一个 Dataset（Dataset 删除时级联删除）和创建者；Fork 生成新的 Conversation 并复制已有的问答。
- **Question / Answer**：Answer 包含状态（生成中 / 已完成 / 已中断 / 失败）、结论文字、所用查询、可选的 Chart、token 用量和耗时。
- **Chart**：包含 ChartSpec、查询、Snapshot 引用、来源 Dataset 引用（Dataset 删除时置空，此后 Chart 仍按 Snapshot 显示但不能修改字段）、标题和说明。会话里的 Chart 属于某个 Answer；Pin 时复制出一个新的 Chart 属于 Board。
- **Snapshot**：单独一张表，JSONB 存储查询结果，行数上限 5000。一旦写入就不再修改；字段变化时生成新的 Snapshot。
- **Board**：包含布局（每张图表的位置和大小）和创建者。
- **Share Link**：包含高熵随机令牌（不是资源 ID）、Board、过期时间、撤销时间。
- **AI Quota 用量**：每个（User、北京时间日期）一行，记录已用次数和当日上限。
- 删除一律**硬删除**，通过外键规则保证一致性；对象存储里的文件由定时任务异步清理。
- 数据库结构变更通过 drizzle-kit 生成迁移文件并提交到仓库；部署时先执行迁移，再启动应用；生产环境禁止使用 push。
- 资源 ID 用不可猜测的随机 ID；工作区在 URL 中用 slug。

### 路由

```
/                                         首页（产品介绍 +「一键体验」）
/login  /signup                           认证路由组
/invite/[token]                           接受邀请
/w/[workspaceSlug]                        工作区首页（最近的会话和看板）
/w/[workspaceSlug]/datasets/[datasetId]   Profile + Column Description
/w/[workspaceSlug]/c/[conversationId]     Conversation
/w/[workspaceSlug]/boards/[boardId]       Board（图表详情用拦截路由 + 并行路由以弹窗打开）
/w/[workspaceSlug]/settings/members       成员与邀请
/s/[shareToken]                           公开分享页（不需要登录，noindex）
```

`/w/[workspaceSlug]` 的 layout 统一校验成员身份，并提供 WorkspaceProvider。

### 数据上传链路

1. 浏览器在本地解析文件：CSV 直接交给 DuckDB，XLSX 先用 SheetJS 转换。
2. 浏览器在本地推断列类型、用 DuckDB 生成 Profile、抽取少量样本行，并导出为 Parquet。
3. 服务端创建一条"等待上传确认"状态的 Dataset，并签发预签名的上传 URL；浏览器用它直接把文件上传到对象存储，不经过应用服务器。
4. 浏览器通知服务端上传完成，服务端校验后把 Dataset 置为就绪，保存列结构、Profile 和样本行。
5. 超时仍未确认的 Dataset 及其文件由定时任务清理。
- 大小上限：普通用户 50MB，Guest 10MB，在浏览器和服务端签发 URL 时都要校验。

### 查询执行（ADR-0004、0005、0009）

- 所有查询都在成员浏览器里的 **DuckDB-WASM** 中执行，服务端从不执行 AI 生成的查询。
- **查询引擎模块**（不依赖 React，模块内单例，第一次使用时才启动）对外提供：预加载、获取引擎实例、`loadDataset`（先查 OPFS 缓存，没有再调用传入的下载函数，然后注册文件、建内存表、锁定配置）、`query`（先做 SQL 安全检查，再执行，结果行数设上限）、`profile`。下载 Parquet 的方法由调用方注入，引擎不知道预签名 URL 的存在。
- 直接使用 DuckDB-WASM 自带的 `AsyncDuckDB`（本身已在 Worker 中运行），选单线程的 `eh` 版本，不开 COOP/COEP。WASM 等文件放在自己的域名下，设置 immutable 长缓存。
- Parquet 以 datasetId 为 key 缓存在 OPFS（预签名 URL 每次都不同，HTTP 缓存永远不会命中；Dataset 不可修改，缓存永不失效，只按容量淘汰）。
- **SQL 安全三层防御**：(1) 数据加载进内存表后关闭外部访问、锁定配置、禁止扩展的自动安装和加载；(2) 执行前用 DuckDB 自带的解析器确认只有一条 SELECT 语句；(3) 全站 CSP 的 `connect-src` 白名单，Worker 脚本的响应也要带上。
- 每个 Chart 生成或字段被修改时都保存一份 Snapshot；查看 Conversation、Board、Share Link 时一律读快照渲染。只有提问或手动修改字段时才加载查询引擎和原始数据。

### AI 链路

- 通过 **AI SDK** 调用 **DeepSeek**，经由 provider 抽象接入，可以替换成通义千问；测试时替换成 mock 模型（这是 S1 的注入点）。
- 一次提问的流程：
  1. 客户端把 Question 发给流式输出接口。服务端依次校验身份、角色和"是否为会话创建者"，然后原子地扣减 AI Quota，保存 Question，并创建一条"生成中"的 Answer。
  2. 服务端调用模型。提示词包含列结构、Column Description、Profile 摘要和样本行，要求用中文回答。提供两个工具：`runQuery`（不在服务端执行，交给客户端）和 `showChart`（参数按 ChartSpec schema 校验）。
  3. 客户端在 `runQuery` 回调里用查询引擎执行，把截断后的结果（前几十行和总行数）或报错回传给模型；模型最多自我修正 3 轮。
  4. 生成结束后，客户端用最终的查询算出完整的快照并上传，服务端保存 Chart 和 Snapshot，把 Answer 置为"已完成"。
  5. 客户端中途离开：Answer 置为"已中断"，不退还额度。模型接口报错或超时：Answer 置为"失败"，并退还额度。两种状态都可以重新生成。
  6. 记录 token 用量和耗时，写进结构化日志。
- 问题无法用当前数据回答时：只给文字说明，不出图表，并附 2 到 3 个 Suggested Question；这次提问照常计入额度。
- 快照数据来自客户端，服务端无法验证其真实性。能伪造快照的只有这个工作区的 Editor，而他们本来就能上传任意数据，所以这个风险可以接受。
- AI 输出的 Markdown 渲染时不允许原始 HTML。

### AI Quota 与限流

- 扣减用一条带条件的原子 UPDATE 完成（只有已用次数小于上限时才加 1，并返回结果），天然防止并发超扣；日期按北京时间计算，第二天自然是新的一行，不需要定时重置。
- 额度：普通用户每天 50 次，Guest 每天 20 次。AI 内部为修正错误而自动重试的调用不计入。
- 鉴权接口的限流用 Better Auth 内置功能，计数存在数据库里；"一键体验"每个 IP 每天最多创建 3 个 Guest。

### ChartSpec 与图表渲染（ADR-0002）

- ChartSpec 是项目自己定义的精简格式：图表类型、x/y 字段映射、分组（系列）字段、聚合方式、排序、标题等。只有一个 Zod schema，同时用于四个地方：AI 的 `showChart` 工具定义、图表调整面板的校验、数据库 JSONB 字段的类型、SSR 渲染的输入。
- 支持 8 类图表：柱状图（含堆叠）、折线图和面积图、饼图和环形图、散点图、表格、热力图、中国省份地图（自行引入 GeoJSON）、KPI 数字卡。
- ChartSpec 到 ECharts option 的映射是纯函数，服务端和客户端共用。ECharts 的主题从全站 CSS 变量生成。
- 统一的图表渲染组件有两种模式：交互模式（会话和看板：进入视口时才初始化，按图表类型使用固定高度）和静态模式（分享页：服务端直出 SVG；用户开始交互或浏览器空闲时，再加载完整的 ECharts 接管）。
- 图表调整面板要能判断是否需要重新查询：只换图表类型不需要，改了字段或聚合方式就需要。

### 分享页（ADR-0006）

- 由 RSC 读取快照，服务端用 ECharts 的 SSR 能力输出 SVG，首屏不加载图表 JS。
- 页面内容按 boardId 打缓存标签，Board 被编辑时让标签失效；但**撤销和过期每次请求都实时校验，不走缓存**。
- 页面设置 `noindex`；只输出图表，不输出原始数据和对话。
- Share Link 显示 Board 的最新状态。

### 前端架构（ADR-0011）

- 分层（依赖只能从上往下，由 lint 强制）：路由层（RSC 取数据、组合 feature）→ 界面层（按 feature 划分的组件）→ React 适配层（很薄的 hook）→ 模块层（不依赖 React：查询引擎、ChartSpec 映射、状态机）→ 通用工具。
- 按业务领域划分 feature：auth、workspace、dataset、conversation、chart、board、share，名称和 CONTEXT.md 的术语一致。一个 feature 只能通过另一个 feature 的公开出口引用它；服务端代码都标记为 server-only。
- 异步状态统一用带标签的联合类型；有明确生命周期的流程（上传、粘底、客户端的 Answer 生命周期）写成手写的带类型 reducer，不用 XState。
- 开启 React Compiler，默认不手写 useMemo、useCallback、memo；只有测量证明需要的地方才手动加，并记录进性能日志。
- 状态划分：服务端数据走 RSC 和 Server Action + revalidate；客户端拉取的数据（目前只有快照，以及按 (datasetId, sql) 缓存的查询结果）走 TanStack Query，`staleTime: Infinity`；跨组件的编辑中状态用归属于某个 feature 的 Zustand store；可以分享的界面状态放在 URL 的 searchParams 里。
- Provider：根 layout 只放 QueryClientProvider 和 ThemeProvider；工作区 layout 放 WorkspaceProvider，只存工作区、成员和角色这类很少变化的身份信息；查询引擎不用 Context。
- **Hook 清单**：
  - 通用：`useInViewport`、`useServerAction`、`usePrefersReducedMotion`
  - 工作区与权限：`useWorkspace`、`useCan`
  - 数据集和查询：`useDatasetUpload`、`useDatasetReady`、`useDatasetQuery`
  - 图表：`useSnapshot`、`useEChart`、`useChartTheme`、`useChartSpecEditor`
  - 会话：`useConversationStream`（包装 AI SDK 的 useChat）、`useStickToBottom`、`useVirtualAnswers`
  - 看板：`useBoardLayout`（乐观更新、防抖保存、失败回滚，对外暴露 `dragging` 状态）
- **会话虚拟列表**（ADR-0007）：基于 @tanstack/react-virtual 自己实现，粘底和滚动锚定也自己实现。判断用户是否主动离开底部，依据的是滚轮、触摸、键盘等用户意图事件。Answer 里的图表按类型使用固定高度（骨架屏同样尺寸）。粘底规则：
  1. 打开会话时直接定位到最后一条；
  2. 发送提问时平滑滚到底部，并进入跟随状态；
  3. 流式输出时，处于跟随状态就保持在底部；用户主动上滚时立即退出跟随；
  4. 退出跟随后显示"回到底部"按钮，有新内容时带提示点；用户滚回距底部约 80px 以内时自动恢复跟随；
  5. 视口上方的条目高度变化时，正在阅读的内容不跳动；
  6. 系统设置了减少动画时，关闭所有平滑滚动。

### 性能

- **预算**：分享页 LCP < 2.0s（从国内访问、模拟 4G 网络）；看板拖拽 INP < 200ms；首页和分享页首屏 JS 压缩后 < 150KB。
- **看板**：图表进入视口才初始化，离开视口很远后销毁；默认 SVG 渲染器，点数多时换成 Canvas；拖拽过程中不触发 ECharts 重算尺寸，松手后计算一次；折线图开启 LTTB 降采样，散点图开启大数据量模式。
- **会话**：流式输出每约 50ms 渲染一次；Markdown 只对正在输出的那一段增量解析；快照数据在条目进入视口时才拉取。
- **加载策略**：DuckDB-WASM、ECharts（按需引入）、SheetJS（只在上传 XLSX 时加载）都懒加载；进入工作区后在浏览器空闲时预先启动查询引擎，鼠标悬停在会话链接上时提前开始加载。
- **快照接口**：设置 `Cache-Control: private, immutable`。
- **字体**：中文使用系统字体栈；英文和数字用 next/font 自托管 Inter，并启用等宽数字。
- **测量**：Lighthouse CI 检查预算，超标则 CI 失败；PR 评论显示 bundle 体积变化；用 web-vitals 采集真实用户指标，上报到错误监控平台（自托管 GlitchTip 或 Sentry）；每项优化都在性能日志中记录问题、测量方法和前后数字。

### 工程约定

- pnpm；通过 packageManager 字段和 .nvmrc 锁定 Node LTS 版本；TypeScript strict 并开启 noUncheckedIndexedAccess。
- ESLint flat config：typescript-eslint 类型感知规则、react-hooks、jsx-a11y、eslint-plugin-boundaries；Prettier 加 Tailwind 插件自动给 class 排序。
- husky + lint-staged 在提交前检查改动过的文件；commitlint 强制 Conventional Commits。
- UI：Tailwind v4（用 `@theme` 声明设计变量）+ shadcn/ui（视为第三方代码，定制时在 feature 里包一层）；组件默认是服务端组件，`'use client'` 只加在叶子组件上；不做 Storybook。
- 环境变量用 @t3-oss/env-nextjs 在启动时校验；数据库的插入和更新校验由 drizzle-zod 从表结构生成。
- Git 流程：每个 Issue 开一个短期分支，通过 PR squash 合并到 main；main 开启分支保护；使用 PR 模板；Renovate 每周合并一次依赖更新。
- CI（在 PR 上运行）：安装依赖（带缓存）→ 并行执行 lint、类型检查、单元测试 → 集成测试（Postgres 服务容器）→ 构建 → 端到端测试 → Lighthouse CI → bundle 体积评论。合并到 main 后再构建 Docker 镜像并推送到 GHCR。
- 定时任务：带密钥保护、可重复执行的 `/api/cron/[job]` 路由，由外部调度器触发。任务包括：清理过期的 Guest、清理没有确认上传的 Dataset 和文件、删除已删除 Dataset 的文件。

### 移动端

- 分享页和会话页做响应式；看板编辑和 Profile 页只适配桌面端，手机打开时提示"请在电脑上编辑"。

## Testing Decisions

**什么是好的测试**：只通过接缝的公开接口验证外部可观察的行为（输入 → 输出、状态变化、数据库状态），不断言内部实现（私有函数、调用次数、组件内部 state）。重构内部实现时，测试不应该需要修改。

**测试接缝**（已和开发者确认）：

- **S1 浏览器端到端测试（Playwright）**：通过真实页面驱动。大模型在模型提供者这一层替换成按脚本回答的 mock 模型，这是唯一需要为测试专门留出的注入点。覆盖三条主流程：
  1. 注册或登录，以及一键体验；
  2. 上传数据集、提问、看到图表；
  3. Pin 到看板、创建 Share Link，外部访客能看到图表但看不到原始数据。

  同时用 axe 检查可访问性。
- **S2 业务用例层（Vitest + 真实 Postgres）**：直接调用业务用例，传入"谁在操作"和输入，断言返回结果和数据库状态，不经过 Next.js。覆盖：
  - 权限矩阵的表格驱动测试（角色 × 操作 × 期望结果）；
  - 跨租户访问；
  - AI Quota：原子扣减、并发不超扣、失败退还、中断不退、按北京时间计算日期；
  - 删除 Dataset 的连带规则；
  - Share Link 的撤销和过期；
  - Guest 的各项限制和"一键体验"的 IP 限流；
  - Answer 状态的流转；
  - 最后一个 Owner 不能退出。
- **S3 查询引擎接口（Vitest 浏览器模式，运行真实的 WASM）**：调用 `loadDataset` / `query` / `profile`，下载函数用注入的假实现。覆盖：
  - 外部访问被拒绝，比如读取远程 URL 的查询失败；
  - 非 SELECT 语句和多条语句被拒绝；
  - 结果行数上限；
  - OPFS 缓存命中后不再调用下载函数。
- **S4 图表渲染（Vitest + ECharts SSR）**：输入 ChartSpec 和 Snapshot，输出 SVG。覆盖 8 类图表的 SVG 快照对比，以及非法的 ChartSpec 被拒绝。
- **S5 状态机 reducer（Vitest，纯函数）**：输入一串事件，断言最终状态。覆盖：
  - 粘底：区分用户主动滚动和程序滚动、回到底部后恢复跟随、有新内容时的提示；
  - 上传流程：包括取消和各个阶段的失败；
  - 客户端的 Answer 生命周期。

**刻意不设接缝**：hook 和组件（hook 很薄，由 S1 覆盖）、ChartSpec 到 option 的中间结构（由 S4 的 SVG 输出覆盖）、数据访问层（由 S2 覆盖）。

**不设硬性覆盖率百分比**，但业务用例层和上述核心逻辑必须有测试。Lighthouse 预算和 bundle 体积属于 CI 门禁，不算测试。

**已有的测试可参考**：没有。仓库目前只有文档，这份规格就是第一批测试的来源；第一个落地的 S2 和 S5 测试会成为之后测试的参照范例。

## Out of Scope

- 连接外部数据库（Postgres、MySQL 等），见 ADR-0003
- 邮箱验证、找回密码，以及任何邮件发送
- 图表之间的联动筛选（v2）
- 国际化（v2；界面和 AI 回答都只用中文）
- 操作审计日志（v2）
- 导出 PNG、PDF（v2）
- Postgres 行级安全（RLS），v2
- 跨数据集 JOIN；一个 Conversation 只针对一个 Dataset
- 在 Board 上让 AI 修改图表（只能在 Conversation 里）
- 多人实时协同编辑同一个看板
- 手机端编辑看板、查看 Profile
- Redis、消息队列、独立的后端服务
- Storybook
- 任何形式的中后台和内部管理系统
- 部署目标的最终选择（见 Further Notes）

## Further Notes

- **项目定位**：这是一个面向校招的作品集项目，目标岗位是大厂前端和 AI 产品前端。取舍标准是"每个方案在面试时都能讲出具体的问题和对应的解法"，并且看起来像企业级产品，而不是个人玩具。
- **部署方式尚未决定**：两个候选是 Vercel + Neon + R2，以及香港轻量服务器 + Docker Compose（Next.js standalone、Postgres、RustFS、Caddy）。当前倾向后者，因为国内面试官能稳定打开。代码一律按 S3 兼容接口编写，第一次上线前再定。注意：OpenAI 和 Anthropic 的 API 不支持中国大陆和香港地区，这也是选择 DeepSeek 的原因之一。
- **讨论中没有明确、这里采用的默认值**：
  1. 看板布局在并发编辑时，后保存的覆盖先保存的；
  2. 演示数据用脚本生成的合成数据，避免版权问题；
  3. Invite Link 在使用一次后失效。
- **性能日志**是面试的核心素材：每项优化都要在仓库的性能日志中留下测量方法和前后数字。
- 开发主要由 AI 完成，所以约定必须由工具强制执行（lint、类型检查、CI、分支保护），不能只写在文档里。
